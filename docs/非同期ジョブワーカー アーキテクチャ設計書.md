# **非同期ジョブワーカー アーキテクチャ設計書**

## **1\. 設計方針 (Design Philosophy)**

本プロジェクトでは、FastAPI (API) と Worker (非同期処理) を疎結合に保ちつつ、堅牢な型安全性とテスト容易性を確保するために以下の設計を採用する。

### **コア・コンセプト**

1. **Common as a Contract (契約としてのCommon)**: common ディレクトリには、APIとWorkerが会話するための「データ定義 (Schema)」と「インターフェース (Protocol)」のみを配置する。**処理ロジックは一切含めない。**  
2. **Worker Service Pattern**: Worker内の処理は「Processor」ではなく「Service」として定義し、DI (依存性注入) を活用する。  
3. **Typed Execution (Pattern B)**: WorkerのServiceは、辞書型 (dict) ではなく、**厳密に定義されたPydanticモデル** を引数として受け取る。データのパースとバリデーションは、Serviceが呼ばれる手前（Dispatcher）で完了させる。

## **3\. コンポーネント詳細**

### **3.1 Common (Shared Contract)**

APIとWorkerの「共通言語」を定義する。

インターフェース定義 (common/core/interfaces.py)  
WorkerのServiceが満たすべき契約。Pattern Bを採用するため、引数はジェネリックまたは Any とするが、実装クラスでは具体的な型を扱う。

Python

from typing import Protocol, Any, runtime\_checkable  
from common.core.result import Result

@runtime\_checkable  
class IWorkerService(Protocol):  
    """全てのWorker Serviceが実装すべきインターフェース"""  
    async def execute(self, payload: Any) \-\> Result\[None, Exception\]:  
        ...

**スキーマ定義 (common/domains/email/schemas.py)**

Python

from typing import Literal  
from pydantic import BaseModel, EmailStr

class EmailJobPayload(BaseModel):  
    job\_type: Literal\["send\_email"\] \= "send\_email"  
    recipient: EmailStr  
    subject: str  
    body: str

### ---

**3.2 Worker Service (Implementation)**

ビジネスロジックの本体。「Processor」ではなく「Service」と呼称し、必要な依存関係を \_\_init\_\_ で受け取る。

**実装ルール:**

1. **Typed Argument**: execute メソッドの引数は、dict ではなく **具体的なPydanticモデル** (EmailJobPayload) を指定する。  
2. **Dependency Injection**: 外部クライアント（SMTP, S3など）はコンストラクタで受け取る。

**コード例 (worker/app/domains/email/service.py)**

Python

from typing import Any  
from common.core.result import Result, Success, Failure  
from common.domains.email.schemas import EmailJobPayload

class EmailWorkerService:  
    def \_\_init\_\_(self, smtp\_client: Any):  
        self.smtp\_client \= smtp\_client

    \# ★ Pattern B: 具体的な型 (EmailJobPayload) を受け取る  
    async def execute(self, job: EmailJobPayload) \-\> Result\[None, Exception\]:  
        try:  
            print(f"Sending email to {job.recipient}")  
            \# await self.smtp\_client.send(...)  
            return Success(None)  
        except Exception as e:  
            return Failure(e)

### ---

**3.3 Worker Dispatcher (The Core Mechanism)**

「Pattern B」を実現するための核心部分。  
ジョブタイプ文字列に基づき、「どのスキーマでバリデーションし」「どのサービスに渡すか」を制御する。  
**コード例 (worker/app/core/dispatcher.py)**

Python

from typing import Any, Type  
from pydantic import BaseModel  
from common.core.interfaces import IWorkerService

class JobDispatcher:  
    def \_\_init\_\_(self):  
        \# ServiceとSchemaをセットで保持する  
        self.\_registry: dict\[str, tuple\[IWorkerService, Type\[BaseModel\]\]\] \= {}

    def register(self, job\_type: str, service: IWorkerService, schema: Type\[BaseModel\]):  
        """ジョブタイプに対し、実行するServiceと、変換に使うSchemaを登録する"""  
        self.\_registry\[job\_type\] \= (service, schema)

    async def dispatch(self, job\_type: str, raw\_payload: dict) \-\> Any:  
        entry \= self.\_registry.get(job\_type)  
        if not entry:  
            raise ValueError(f"Unknown job type: {job\_type}")  
          
        service, schema\_cls \= entry  
          
        \# 1\. ここでPydanticモデルへ変換 (Validation)  
        \#    失敗した場合は即座に例外となり、Serviceは汚染されない  
        typed\_payload \= schema\_cls.model\_validate(raw\_payload)  
          
        \# 2\. 型付きオブジェクトをServiceへ渡す  
        return await service.execute(typed\_payload)

### ---

**3.4 Wiring (Main Entrypoint)**

Worker起動時に、Dispatcherに対して依存関係を注入したServiceを登録する。

**コード例 (worker/app/main.py)**

Python

from worker.app.core.dispatcher import JobDispatcher  
from worker.app.domains.email.service import EmailWorkerService  
from common.domains.email.schemas import EmailJobPayload

\# 依存関係の構築 (DI)  
def build\_dispatcher() \-\> JobDispatcher:  
    dispatcher \= JobDispatcher()  
      
    \# Email Serviceのセットアップ  
    email\_service \= EmailWorkerService(smtp\_client=...)  
      
    \# ★ ServiceとSchemaを紐付けて登録  
    dispatcher.register(  
        job\_type="send\_email",   
        service=email\_service,   
        schema=EmailJobPayload  
    )  
      
    return dispatcher

## **4\. データフロー (Data Flow)**

1. **API**: User \-\> Router (Validate EmailJobPayload) \-\> SQS (JSON serialize)  
2. **Queue**: JSON Message ({"job\_type": "send\_email", "recipient": ...})  
3. **Worker (Loop)**:  
   * SQSからメッセージ受信 (JSON)  
   * Dispatcher.dispatch(type, json) を呼び出し  
   * **Dispatcher**: JSONを EmailJobPayload オブジェクトに変換 (Validation)  
   * **Service**: execute(job: EmailJobPayload) が呼ばれる  
   * **Logic**: 型安全な状態でビジネスロジック実行

## **5\. この設計のメリット**

* **完全な型安全性**: WorkerのService内部では、データが正しい型であることが保証されているため、job\["recipient"\] のような辞書アクセスや、型チェック処理が不要になる。  
* **責務の分離**:  
  * common: 「何をするか（定義）」  
  * dispatcher: 「データの翻訳（変換）」  
  * service: 「どう処理するか（ロジック）」  
* **テスト容易性**: ServiceクラスはPydanticモデルを受け取る普通のクラスであるため、単体テストが容易。Dispatcherを介さずにテストができる。
